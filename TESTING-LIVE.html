01

关键结论

先给判断，再给明细；下面每一节都能追到具体用例与日志。

成本结构

判断类问题全部压在秒级层，E2E 只负责它独有的风险

111 条 Node 断言跑完约 0.22 秒，E2E 的 102 条需要 1–2 分钟。因此凡是纯函数层能判定的，一律不放到 E2E —— 后者只验证真实渲染、页面流程与原生行为。

覆盖重心

页面层占 42%，且其中 81% 是本项目专属语义

47 条页面断言里 38 条围绕"锁定式推进、达标解锁、三态列表"等产品规则。这类断言最值钱，也最需要绑定依据（验收清单 / 来源快照），否则会随需求腐化。

数据可信

60 式标准逐条对回来源快照，差异必须在案

58/60 一字不差，2 处刻意修正在测试里有记录，并有"反向断言"防止有人改快照让数据看起来对齐。

已知缺口

视觉基线的余量偏薄，且基线本身不判对错

同代码跨会话重跑时噪声已达 5 行坏行，触发线是 6 行；基线记录的是"上次被认可的样子"，对错仍由人工审批与上游规范决定。

04

未满足项与误判风险

测试自身的输出同样可能骗人。以下三种情况本项目都实际遇到过，均已加守卫。

E2E · 条数守卫

场景中途崩溃却报全绿

脚本内含 EXPECTED_CHECKS = 102：实际通过条数与期望不符即报警，不给"中止即成功"的机会。

截图 · 几何守卫

19 张被误判为"全部变化"

工具窗口尺寸改变（363×785 → 377×813）会使指纹逐行失配。现改为单独提示"环境尺寸变化、不可比"，不再逐张报红。

截图 · 空白补拍

空白图被当成成功

加了体积下限，并只对"空白"补拍一次；断言失败、页面报错照旧抛出 —— 补拍不等于把红改绿。

在本机运行

前置：Node ≥ 20（本机 24）与微信开发者工具（E2E 与截图需要它，且需图形环境）。

npm testnpm run e2e:servenpm run e2enpm run e2e:shots

跑 E2E 期间不要修改项目文件（会触发重编译并清空页面栈）。E2E 不进 CI：它需要图形环境，跑不了就不假装绿，CI 只跑 npm test。
