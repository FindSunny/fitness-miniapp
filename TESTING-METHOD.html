1开发主旨：六条主张，各排除一种错误做法

这一节解决：为什么先谈开发主旨？—— 因为主张决定了哪些不变量存在，不变量才决定了断言该写什么。

设计主张一句话解释它排除了什么错误做法
状态只有一个真相进度真相 = 每一式的"已通过"时间戳；"当前式"是推导出来的（第一个没通过的式），不是存储字段❌ 再存一个"用户选中的式"→ 达标了但没点按钮，状态就不动（这个 bug 真实发生过）
锁定式推进（不能跳级）只有"已通过的式"和"当前式"能记录，后面的只能看❌ 允许跳级 → 动作变形、也退化成"动作库"，且"多个进行中"这类说不清的状态会出现
一份数据驱动全部页面60 式（含三档标准、单位、每侧、示意图、要点、器械）全在一个 arts.js 里❌ 把文案与标准写进页面 → 改一处要翻十个文件，且页面之间会互相打架
零后端 · 数据只存本机无 wx.login、无用户信息 API、零网络请求；进度存 wx.storage❌ 为了"排行榜"先上后端 → 立刻背上隐私声明、域名备案、冲突合并（这些是 v2 的事）
自撰内容，版权红线示意图自绘、动作要点自撰；只用公开的动作名称与标准数据❌ 搬运原书文字与插图 → 版权风险；也❌ 把自撰要点说成"权威教材"
文案不能说做不到的事首页写"不用专业器械"而不是"零器械"（引体要单杠、倒立撑要墙）❌ 用夸张宣传语 → 用户第一次就发现被忽悠（我们真的差点写"零器械"）
为什么这一节要放在最前面

如果主张只是"我们打算这么写"，那它跟测试无关。但只要主张被写成不变量（"存储里不能再出现 currentNo""未解锁的式不能写入记录"）， 它就变成可执行、可复算、可回归的东西 —— 这就是下一节的枢纽。

3断言的三种成分：定制化断言为什么值钱

这一节解决一个反问："你的断言都是为这个项目定制的，别人怎么用？"—— 先把事实摆出来，再说它的代价与出路。

A 领域定制 68 条（61%）
C 混合/工具 28 条（25%）
B 通用工程 15 条（14%）

统计口径：111 条 Node 断言按"这条断言换个项目还能不能直接用"分类。 其中 page-flow（47 条）里 38 条是领域定制 —— 页面层几乎是纯定制的，这符合直觉：页面层守的就是产品语义。

成分例子特点与对策
A 领域定制 "未解锁的式不能写入记录"、"达标后'进行中'恒为 1 行"、"三档标准必须单调递增" 最值钱，也最短命：它们守住的是产品语义（真正的差异化），但只要产品改语义就会失效。
对策 = 绑依据：每条定制断言都要能指回一份"上游真相"——ACCEPTANCE.md 的状态表、来源快照、或某个真实 bug 的编号。
B 通用工程 WCAG 对比度、字号下限、点按区、禁用纯黑纯灰、PNG 解码确定性、视觉基线稳定性 最可迁移：这 15 条里 10 条是"界面质量 + 图片工具"类，任何前端项目可以直接抄。
它们的共同点：判据是算出来的（公式/阈值），不是"我觉得"。
C 混合 / 工具链 晋级判定边界（组数够数值不够 / 乱序 / 非法值）、存储重置语义、E2E 条数守卫 抽象一下就能复用：把"领域对象"换成参数即可。比如判定边界那组，本质是"多维阈值判定"的通用测试法。

抽象路径：定制断言 → 参数化 → 模板化

① 定制态（本项目里真实的样子）
// 只有这个产品读得懂：把"囚徒健身"的语义写死在断言里
assert.strictEqual(
  store.pendingSets(), 0,
  '未解锁的式不该写入训练记录'
);
② 抽象态：状态机守卫断言（可直接复用的形态）
// 把"谁能操作谁"抽成数据，断言变成一条通用规则
const guards = [
  { when: 'locked',   action: 'record', allowed: false },
  { when: 'current',  action: 'record', allowed: true  },
  { when: 'passed',   action: 'record', allowed: true  }
];
// 任何"只有处于状态 A 才能做 X"的产品都能套这张表

这条路我们只走了一半：已经参数化（三档标准、每侧、计时/计次都是数据）， 但"领域语义"仍然写在断言名字与预期里。诚实地说：领域断言不可能完全通用 —— 能通用的是"如何组织它们"（一张状态×动作的守卫表、一份上游真相、一条回归留痕），而不是它们的字面内容。

4方法论总结：八条可迁移的原则

这一节解决：把上面的做法压缩成能带走的东西。每条都是"一句话结论 + 本项目证据 + 边界"。

#原则本项目证据边界 / 反例
1先写语义，再写测试，最后改代码访谈给的是现象（"列表没反应"），先翻译成状态表（ACCEPTANCE.md 第一节），再写测试，最后才动代码语义没定就写测试 = 把猜测固化下来
2断言"用户看得见什么"，不是"实现返回了什么"早期断言 stateText === '未开始'（照着当时的实现写）→ 改成语义断言后，同一类 bug 立刻暴露纯函数层仍要断言返回值 —— 但那是"其中一层"，不是全部
3必须测"往返"：操作 → 离开 → 回来真机验收发现"记录丢失/历史看不见/状态不跟随"都出在这条缝里同一页面实例上断言再多也抓不到
4低层能抓的，别留到高层111 条 Node 断言 0.15 秒；102 条 E2E 要 2 分钟。数据错一个数字，界面完全看不出来 —— 只有 L1 能拦反过来：真实渲染、手势、原生组件行为，只有 E2E/真机能看到
5定制断言要绑"上游真相"来源快照 + 差异必须在案；验收清单编号写进测试名（"验收 36"）不绑依据的定制断言，半年后没人敢改
6先怀疑测试，再怀疑代码三个"测试在撒谎"：场景崩溃报通过、空图算成功、断言全绿但东西是坏的（详见第 9 节）光加断言不够，还要给"断言本身"加守卫（条数、产物有效性）
7量出来再定阈值，别拍视觉基线的容忍度是 7 组对照量出来的（噪声 0.41%–0.54% vs 真变化 1.63%–54.7%）事后给噪声加白名单 = 掩盖，不是解决
8明确写下"自动化覆盖不了什么"TESTING.md 第七节：真机手感、跨进程持久性、审美、内容正确性 → 交给验收清单与真人把"只有人能验的"混进通过率，等于自己骗自己

覆盖不了为什么谁来做

7实现：E2E 怎么驱动真实小程序

这一节解决：没有浏览器、没有 DevTools 插件的情况下，怎么在真实运行时里断言、又怎么稳定下来？

为什么不用坐标点击

element.tap() 在自动化实例里点不到 bindtap（试过多轮）； page.callMethod() 也取不到页面方法。 最后改成：在 App 侧用 getCurrentPages() 拿到页面实例，直接调它的处理函数 —— 代码路径完全一样，只是不经过手指坐标。

稳定化三件套
  • 调真实处理函数（而不是点坐标）
  • 探针 + 重试：data() 当探针，节点没就绪就重试；页面切换先等 waitForPage
  • 期望条数常量：EXPECTED_CHECKS = 102，条数对不上直接报警（防"中途崩了却报全绿"）

evaluate 里写 setDatatimeout waiting for automator response用 SDK 的 page.setData()，且每次重新取栈顶页面

8实现：截图能做"视觉回归"，但要先量噪声

这一节解决：能不能用截图对比盯住界面？能，但最朴素的方案（整图哈希）一定失败 —— 我们是量出来才定方案的。

噪声源实测现象解法
状态栏实时时钟 + 电量同一状态隔 70 秒截两张，整文件哈希必不同（12:17→12:19，还多出一个 "100"）裁掉顶部 48 行（实测 40/60/80/120 都稳定）
重启工具后渲染位移约 1px导航栏标题字形整体下移 1 行、最大通道差 255；纯哈希会报"19 张全变了"（狼来了）改用行暗度指纹（每行暗像素个数）：黑像素只在相邻行间挪一点，指纹几乎不变
模拟器几何尺寸变化以最小化方式启动工具，图从 363×785 变成 377×813，指纹逐行比就失效比对前先查尺寸：几何变了就单独提示"这不是内容变化，恢复窗口或重建基线"
空白截图一张 10KB 白板被当成 ✓（"产物存在即成功"）体积下限 + 空白自动补拍一次（只对空白补拍，断言失败照旧抛出来）
阈值是量出来的，不是拍的
对照（7 组真实实验）坏行占比判定
跨 IDE 会话（同页面，含 1px 位移）3–4 / 737 = 0.41%–0.54%没变 ✓
大面积线稿的全屏大图，跨会话3 / 737 = 0.41%没变 ✓
同一页面换状态（只差一行文案）12 / 737 = 1.63%变了 ✓
完全不同的页面403 / 737 = 54.7%变了 ✓

→ 取"坏行占比 > 0.8% 且坏行 ≥ 5"判定为变了。 另一个实测：同代码、同尺寸、隔几天换会话跑两次，指纹逐字节完全一致的 0 / 19， 但按阈值判定 19 / 19 都"没变" —— 这说明门禁只能靠"容忍环境漂移的指纹"，像素 diff 只能当给人看的证据。 （⚠️ 也说明现有余量偏薄：噪声已摸到 5 行，触发线是 6 行，建议提到 8。）

顺带一条方法论：基线的语义是"被认可"，不是"通过"

视觉基线记录的是"上次有人看过并认可的样子"（对应截图工具的 --update-baseline，BackstopJS 里叫 approve）， 不是"测试通过的样子"。它保证"之后没变"，不保证"这样是对的"。而且要清楚：本项目这 19 张是 "测试夹具 + 开发版"的样子（图里有开发版才显示的诊断条、脚本启动时刻的时间戳、造出来的进度）， 只适合内部回归，不能当设计走查或作品集素材。

function currentNo(art, opts) {
  const o = opts || {};
  if (o.completed) return null;
  const passedMap = o.passed || {};
  const first = art.steps.find(s => !passedMap[s.id]);
  return first ? first.no : null;
}

function canPractice(art, step, opts) {
  const o = opts || {};
  if (o.completed || (o.passed || {})[step.id]) return true;
  const cur = currentNo(art, o);
  return cur !== null && step.no <= cur;
}

function luminance(hex) {
  const [r,g,b] = srgb(hex).map(v => v <= 0.03928
    ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4));
  return 0.2126*r + 0.7152*g + 0.0722*b;
}
function contrast(fg, bg) {
  const a = luminance(fg), b = luminance(bg);
  return (Math.max(a,b) + 0.05) / (Math.min(a,b) + 0.05);
}

★可以直接写进汇报的四句话

  1. 断言从设计主张推导，不从代码补写。"存储里不能有 currentNo""未解锁不能写入记录"这类不变量，才是测试真正的输入。
  2. 定制化的断言是价值来源，不是缺点。它守住的是产品语义；代价是必须绑"上游真相"（状态表 / 来源快照 / bug 编号），否则会腐化。
  3. 越低越便宜，且"便宜的那层"覆盖的是最贵的一类 bug。数据错一个数字，界面完全看不出来 —— 只有纯函数层能拦；而真实渲染与手感，只能交给真机验收。
  4. 先怀疑测试，再怀疑代码。崩溃报通过、空图算成功、断言全绿但东西是坏的 —— 这三类"测试在撒谎"比业务 bug 更危险，必须给测试自己的输出也加断言。
