# Impeccable 评估：对我们 UI 有没有用（有实测数据）

> 对象：[pbakaus/impeccable](https://github.com/pbakaus/impeccable) —— 面向 AI coding agent 的 UI 设计 skill
> （1 个 skill + 24 条命令 + **61 条确定性检测规则** + 浏览器 live 模式；明确支持 DeepSeek Harness）
> 评估方式：**不看 README 下结论，直接拿它扫我们的真实代码**。CLI 版本 4.1.0。

---

## 一、一句话结论

**值得用，但要用对地方。**

| 用途 | 值不值 | 依据 |
|---|---|---|
| 当**小程序的 lint 工具** | ❌ **不值，而且危险** | rpx 盲区 + 不认 wxml → 会给出**假绿**（见下） |
| 当**人工检查清单**（对比度/小字/点按区） | ✅ **立刻见效** | 我按它的规则自己算，抓到 **5 处真实对比度不合格**（含我这轮刚引入的一处） |
| 扫**我们的 HTML 产物**（预览页/报告页/以后的简历页） | ✅ 值得 | 一次扫出 31 条，全是我的页面上的真问题 |
| 24 条 LLM 命令做 **UI 打磨** | 🔶 以后做 UI 时再用 | `critique / typeset / layout / clarify / harden` 正好对应我们的已知缺口 |

## 二、实测记录（这才是判断依据）

| # | 我试了什么 | 结果 |
|---|---|---|
| 1 | `npx impeccable detect miniprogram`（扫目录） | **无输出、exit 0** —— 看起来"全干净"，其实是**目录扫描静默跳过 `.wxss`** |
| 2 | 显式传单个 `.wxss` | ✅ 认（WXSS 就是 CSS 子集）→ 抓到 `art.wxss:41 transition: width`（布局抖动） |
| 3 | 传 `.wxml` | ❌ 不认（exit 0，无输出） |
| 4 | **对照实验**：px 与 rpx 写同一条规则 | `border-left: 5px` → 报 `side-tab`；`border-left: 8rpx` → **不报** |
| 5 | 扫 `preview/index.html` + `TESTING-REPORT.html` | ✅ 31 条：18 对比度 / 6 侧边色条 / 4 内边距 / 2 小字 / 1 布局动画（+12 条 advisory） |
| 6 | 我按它的对比度规则**自己算**小程序色板 | ❌ 11 组里 **5 组不合格**（它自己报不出来，因为它读不了 rpx，但颜色是可算的） |

**第 1 条和第 4 条是这次评估最有价值的发现**：`detect miniprogram` 的"干净"是**假绿**。
这跟我们在测试里踩过的坑一模一样（场景崩溃却报"19/19 通过"、空截图算成功）——
**"工具没报错"不等于"没问题"，得先确认它到底看了什么。**

## 三、它替我们抓到的真问题（我按规则自己算的）

WCAG AA 正文要求 ≥ 4.5:1（大字 ≥ 3:1）。小程序实际用色：

| 判定 | 对比度 | 配对 | 用在哪 |
|---|---|---|---|
| ❌ | **1.48:1** | `#cbd5e1` on `#ffffff` | `.fig-tag`「部分示意图待补」← **我这轮刚加的** |
| ❌ | **2.34:1** | `#94a3b8` on `#f1f5f9` | `.step-state.locked`「未解锁」 |
| ❌ | **2.45:1** | `#94a3b8` on `#f8fafc` | 面板上的浅字 |
| ❌ | **2.56:1** | `#94a3b8` on `#ffffff` | `.light` 类：进度数字、说明文字等（**用得最多**） |
| ⚠️ | 4.34:1 | `#64748b` on `#f1f5f9` | 首页诊断行副标题（只够大字） |
| ✅ | 4.55 / 4.57 / 4.76 / 6.16 / 17.74 | —— | locked 横幅 / 绿色已通过 / `.muted` / 蓝色进行中 / 正文 |

**为什么这对我们特别重要**：这是个**健身 App，会在健身房、户外、手上有汗的时候看** ——
"浅灰小字"在这种场景下是真的看不清，不是合规洁癖。而修起来很便宜：
把 `.light` 从 `#94a3b8` 换成 `#64748b`（4.76:1 ✅）几乎不改变视觉层级。

### 它没抓到、但我们该自己看的

- **左侧色条**：`TESTING-REPORT.html` 里被报了 6 次（`border-left: 5px + border-radius`），
  而**我们十式列表用的是同款写法**（`.step-item { border-left: 8rpx solid }`）—— 因为 rpx，它没报。
  规则原话：*"Thick colored border on one side of a card — the most recognizable tell of AI-generated UIs."*
  → 值得想想：状态用"左侧色条"表达，还是用**圆点/徽标**更清楚、更不"AI 味"。
- **字号下限**：它报了我报告页的 `11.5px body text`。我们小程序有大量 `19–22rpx` = **9.5–11px**（750rpx 制）——
  处在 iOS 建议下限（11pt）附近或以下。
- **`transition: width`**（art.wxss:41 进度条）：规则说得对（动画 width 触发 layout），
  但就我们这种 10 格进度条，性能影响可以忽略；真要改就是 `transform: scaleX()`，成本很低。

### 它对我们**无用**的建议（知情豁免，不是疏忽）

- *"Don't use overused fonts (Arial, Inter, system defaults)"* ——
  小程序主包上限 **2MB**，引一个中文字体动辄几 MB。**我们继续用系统字体**，这是有意识的权衡。

## 四、怎么用（三条，按价值排序）

1. **规则清单当人工检查单**（最有用，0 成本）：对比度、小字、点按目标、侧边色条、字体。
   → 立即产出：上面那 5 处对比度 + 侧边色条要不要换表达方式。
2. **扫 HTML 产物**（0 安装足迹）：
   ```bash
   npx impeccable detect preview/index.html TESTING-REPORT.html
   ```
   适合挂在"改完 HTML 后自查"里。**注意：必须显式传文件，扫目录会漏。**
3. **以后做 UI 打磨时再装 skill**：`critique`（UX 评审）/ `typeset`（字号层级）/ `layout`（间距节奏）/
   `clarify`（文案）/ `harden`（溢出与边界）。
   - live 模式**不能**用在真小程序上（没有浏览器 dev server），**但能用在 `preview/index.html` 上** ——
     而那份预览正是我们镜像真机 UI 的 HTML。**工作流：在预览页上做视觉迭代 → 手工搬回 WXSS。**
   - 装它会在仓库/全局写 skill + **project hook**（`.dsh/skills/`、hook 清单）+ `.impeccable/` 目录；
     装全局还是项目级、要不要 hook，值得单独决定。

---

## 五、结论

- 它对**小程序的样式**基本是瞎的（rpx + 不认 wxml），**别把它当 CI lint** —— 假绿比没有更危险。
- 它的**规则**是有价值的：我们照着算，一次就抓到 5 处真实不合格，其中一处是我这轮新引入的。
- 它对**HTML 产物**（预览页、报告页、以后的作品集页）是真有用，且**不需要安装**就能用。
- 它最有用的地方其实是**提醒了我们一件已经知道但没做的事**：我们从来没系统检查过颜色对比度和字号下限。
  这件事**不需要这个工具也能做**（我上面就是手算的），但它把清单给了我们。
