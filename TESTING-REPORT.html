2四个选型决定

都不是"最佳实践"，是权衡之后的选择 —— 附上理由，方便团队判断能不能照搬。

决定 1 · 测试框架

Node 层零依赖，用内置 node:test

  • 逻辑本来就是 CommonJS 纯函数，require 就能测
  • 小项目里依赖 = 维护成本：不用配 transform，不会被依赖升级搞挂
  • 结果：100 项断言 0.15 秒，随时跑
决定 2 · 必须有 L4

页面层打桩：真实页面代码跑在 Node 里

  • 两个真实 bug 逃过纯函数测试：通关卡 90%、通关后仍推荐它
  • 都不是算法错，是"页面把数据拼错了"
  • 60 行 wx/Page 打桩 → 90% 页面 bug 挡在 0.1 秒内
决定 3 · E2E 选型

官方 SDK，不用第三方模拟器

  • 它连的是小程序真实运行时：导航、wx API、storage 全是真的
  • 第三方模拟器连运行时都不同 → 出差异分不清是 bug 还是模拟不准
  • 但它不等于真机：渲染/字体/性能/跨进程持久性都不覆盖
决定 4 · 稳定性

断言与截图拆成两个 pass

  • 截图历史上不稳定过（page node not found）
  • 断言 pass 不写图，结论以它为准；截图另有独立命令
  • 原则：不让不稳定环节影响结论可信度

3最值得抄的经验：断言要换"视角"

项目里归档了 29 个真实 bug，25 个是用户发现的（真机验收 + 用户访谈）。我自查发现的基本是"工具/文案"类。

用户发现 25
我自查 4

最能说明问题的一次：R2 访谈那轮用户当场带出 3 个可用性 bug —— 而当时 91 项 Node + 85 条 E2E 断言全绿。 因为它们全都在验证"实现是否按我设想的方式工作"。

❌ 反面：用实现的视角写
// 照着当时的实现写 → 等于给自己打分
assert.strictEqual(
  page.data.steps[1].stateText,
  '未开始'
);
✅ 正面：用用户看得见的语义写
// 断言用户看到的那句话 + 里面每个数字
assert.strictEqual(steps[0].stateText, '进行中');
assert.strictEqual(steps[0].stateSub,
  '已练 1 次 · 最近：中级');   // 练过必须看得出来
assert.match(lockHint,
  /达标标准【升级】3 组 × 50次/);  // 数字也要断言

最后那条是我看截图才发现的：提示写的是"距【初级】还差 1 组"，但真正的过关门槛是【升级】3×50。 断言太宽 = 没断言：只断言"提到了第 1 式"，就漏掉了"里面那个数字是错的"。

4比业务 bug 更危险：测试自己在撒谎

这两类问题的共同点是 —— 它们会让后面所有绿灯都不可信。

坑 A：场景崩了，却报"全部通过"
$ npm run e2e ▸ 首页：推荐与六艺卡片 ✓ ▸ ...（只跑了前 3 个场景） ──────────────────────── E2E：19 / 19 通过 exit code 0

真相：一次 page node not found 让第 4 个场景崩溃， 异常被外层 catch 吞掉、只打印不计数 —— 而"通过率"只统计 check()。

修法
  1. 崩溃时补记一条失败：check('场景「X」执行完成', false, err)
  2. 加 EXPECTED_CHECKS = 80：实际条数对不上就报警 + exit 1
⚠ 断言条数异常：本次只跑了 20 条， 期望 80 条 —— 说明中途崩了， 别把它当"通过"。

代价：每次增删断言要改这个常量。值得 —— 这是唯一能发现"测试没跑完"的办法。

坑 B：空截图算成功

在截图前试着滚页面，截出一张 10KB 的白板，脚本照样报 ✓ 12/12。 修法：加体积下限（> 15KB 才算成功；正常图 45–62KB）。

通用原则：凡是"产物存在即成功"的断言，都等于没断言。

flaky 的处理原则（3 条，含"失败点固定 vs 随机"的判断法）
  1. 不稳定层不得影响结论 —— 截图独立成 pass，断言 pass 不写图。
  2. "失败点固定"和"失败点随机"是两类问题
    本轮 E2E 连续两次挂在同一个场景（page node not found）→ 不是 flake，是环境状态退化（开发者工具会话开太久）→ 重启项目窗口即恢复，随后 102/102。
  3. 不要用"重跑一次就过了"糊过去 —— 那是在训练自己忽略红灯。

7诚实边界

分享给团队时最怕的不是方案不够好，而是把"E2E 全绿"讲成"真机没问题"。

自动化能证明
  • 逻辑与状态流转正确（判定 / 推导 / 解锁 / 推荐）
  • 页面把它们正确渲染到了界面上
  • 真实运行时里的导航、存储、弹窗、往返
  • 编译通过、包体积
只能靠人
  • 跨进程持久性：退出小程序再进数据还在吗 —— 模拟器造不出来
  • 真机手感 / 性能 / 字体渲染
  • "好不好看、一眼能不能懂"
  • 图片在真机上的加载速度

没有 CI、没有覆盖率统计、没有视觉回归 —— 单人项目暂未做。

★三句可以直接写进汇报的话

  1. 能在低层抓住的问题，不要留到高层。同一条断言，Node 层 1 毫秒，E2E 层 2 分钟 —— 差 5 个数量级。
  2. 测试的价值取决于断言的"视角"。用实现的视角写，只能证明"代码和昨天一样"；用用户的视角写，才能发现"看起来没坏但就是不对"。
  3. 先怀疑测试，再怀疑代码。崩溃报通过、空图算成功 —— 这类"测试在撒谎"的问题比业务 bug 更危险，要给测试自己的输出也加断言。
